# 分阶段预期输出

本文档对应根目录 README 快速开始里的同样 8 个阶段，说明每一步你应该实际看到什么。引用的输出块都是从
本仓库一次真实运行中原样复制、必要时做了截断说明——没有任何一处是手工编造后冒充程序输出的样例。

第 1-4 阶段完全确定（无模型、无网络，或使用固定的 mock）。第 5-8 阶段依赖真实模型端点：
**具体输出会因模型而异，本文档不对任何成功率做出承诺。**

## 第 1 阶段——安装/环境检查

```bash
python3 -m pip install -r requirements.txt
python3 -c "import jsonschema; print(jsonschema.__version__)"
```

应看到 `4.26.0`（唯一锁定的依赖）。除非你打算给 `live_runner.py` 传 `--transport sdk`，否则不需要
安装 `openai`——默认的 `--transport http` 只用标准库。

## 第 2 阶段——发布完整性校验

在信任后续任何结果之前，先确认你的检出与 `运行代码与说明/release_manifest.json` 一致——下载损坏应该
在这里响亮地失败，而不是在三步之后变成一个令人困惑的测试失败。

```bash
python3 - <<'PY'
import hashlib, json, sys
from pathlib import Path
manifest = json.loads(Path("运行代码与说明/release_manifest.json").read_text(encoding="utf-8"))
bad = []
for entry in manifest["files"]:
    data = Path(entry["path"]).read_bytes()
    if hashlib.sha256(data).hexdigest() != entry["sha256"] or len(data) != entry["bytes"]:
        bad.append(entry["path"])
print("OK" if not bad else f"MISMATCH: {bad}")
sys.exit(1 if bad else 0)
PY
```

应看到 `OK`。这份清单（`kind: "repo_packaging_manifest"`）覆盖的是**当前整个仓库树**打包发布时的
状态——它和 `运行代码与说明/原始release_manifest_frozen.json` 是两份不同的文件：后者只记录原始内部
`kaxinguo_feasibility_v1` 发布的 33 个文件；新清单里的 `frozen_core_manifest_sha256` 字段则对那份
原始清单文件本身做了哈希，用于可追溯性。

## 第 4 阶段——HTTP mock 走查

```bash
python3 运行代码与说明/mock_server.py --bt-test-id episode_001 --step-test-id episode_016
```

打印后会一直阻塞提供服务：

```
[MOCK] serving http://127.0.0.1:8800/v1/chat/completions bt=episode_001 step=episode_016
```

在另一个终端（这里用了一个临时的 `--out-dir`，避免你自己这次运行和已提交在
`运行结果/mock_runs/` 的示例混在一起——原因见下文说明）：

```bash
python3 运行代码与说明/live_runner.py --mock --architecture bt --test-id episode_001 \
  --model mock-model --endpoint http://127.0.0.1:8800 --out-dir /tmp/kaxinguo_mock_walkthrough
python3 运行代码与说明/live_runner.py --mock --architecture step --test-id episode_016 \
  --model mock-model --endpoint http://127.0.0.1:8800 --out-dir /tmp/kaxinguo_mock_walkthrough
```

每次调用都会为写出的每条轨迹打印一行，形如 `<路径>: FINISHED`。

`运行结果/mock_runs/` 里已提交的示例轨迹就是这次走查的真实输出，只不过当时用的是端口 8801 而不是
8800（唯一的区别只是下面 `endpoint` 字段里的端口号）。如果你不加 `--out-dir`，`live_runner.py`
默认也会写到 `运行结果/mock_runs/`——你这次新跑的结果会和这两个已提交的文件**并存**，而不是替换
它们，之后 `summarize_results.py --include-mock` 会把四条轨迹一起汇总（按 `endpoint` 分组，因为
8800 和 8801 不同）。像上面那样用一个临时 `--out-dir`，可以让你自己这次走查保持独立，方便单独查看。

## 第 5 阶段——真实端点预检（依赖模型）

```bash
export OPENAI_API_KEY=sk-...
python3 运行代码与说明/live_runner.py --architecture both --test-id episode_001 \
  --model <你的模型> --endpoint https://your-endpoint/v1
```

`live_runner.py` 会在打开传输层或发出任何调用**之前**，先校验配置并为每种架构构造一个示例请求
（见 `main()` 里的"Preflight configuration"步骤）。如果这一步失败，说明是请求构造/schema 的问题，
还怪不到你的模型——先把这个修好。从这里开始，具体的终端输出完全取决于你的模型和端点，本文档无法为
此展示一份真实的记录。

## 第 6 阶段——小规模 test-id 运行（依赖模型）

命令同第 5 阶段，去掉 `--mock`。关注打印出的 `<路径>: <outcome>` 这一行。`live_runner.py` 可能产生
的 `outcome` 取值有：`FINISHED`、`NEEDS_RESOLUTION`、`STRUCTURAL_FAILURE`、
`DECISION_LIMIT_EXCEEDED`、`TRANSPORT_ERROR`、`ENVIRONMENT_REJECTED`。只有 `FINISHED` 有可能成为
语义上的通过，而且还要等人工评审（第 8 阶段）之后才算——这些 outcome 字符串本身都不是最终结论。

## 第 7 阶段——完整 `--all` 运行（依赖模型）

```bash
python3 运行代码与说明/live_runner.py --architecture both --all \
  --model <你的模型> --endpoint https://your-endpoint/v1
```

这会让全部 48 个场景在两种架构下各跑一遍（共 96 条轨迹）。耗时和成本取决于你的模型与端点——这里没有
一个固定的预期运行时长可以给出。

## 第 8 阶段——评审与汇总

```bash
python3 运行代码与说明/summarize_results.py --runs-dir 运行结果/live_runs
```

专门针对 mock 走查的输出时，要加 `--include-mock`，否则这些轨迹会被悄悄跳过。下面这条命令针对的是
已提交在 `运行结果/mock_runs/` 的那两条示例，不是你自己在第 4 阶段跑出来的结果（如果你按上面的
`--out-dir /tmp/kaxinguo_mock_walkthrough` 示例操作，你自己的结果存在别处——用同样的方式把
`--runs-dir` 指向那个目录即可单独汇总）：

```bash
python3 运行代码与说明/summarize_results.py --runs-dir 运行结果/mock_runs --include-mock
```

`classification` 是 `PENDING_HUMAN_REVIEW`，不是 `HUMAN_CONFIRMED_PASS`，`macro_pass_rate` 也是
`0.0`——因为没有任何人工评审过这些 mock 轨迹（mock 走查的目的是证明管线能跑通，不是产出一个分数）。
要真正把一条轨迹推进到 `HUMAN_CONFIRMED_PASS`/`HUMAN_CONFIRMED_FAIL`，需要打开对应的轨迹 JSON 文件，
把 `human_review.criteria` 下的六个字段（`structure_and_arguments`、`required_observation_evidence`、
`correct_branch`、`all_required_actions`、`constraints_respected`、`completion_at_correct_time`）
都填成 `true`/`false`，再重新跑一次 `summarize_results.py`——它会把你的评审结果合并进该 `run_id`
已有的那一行 `scenarios.csv`，之后再扫一次也不会把它冲掉。

对于真实端点的运行，你的 `scenarios.csv`/`task_pass_rates.csv`/`goals.csv` 会包含你的模型真实的
outcome 以及（评审后）通过率——本文档无法也不会预测这些数字会是多少。
